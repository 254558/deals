# 设计说明 · 优衣库（uniqlo）

这里是合并后的 `deals` 仓库里**优衣库那一半**的设计说明：它为什么这样抓、报告为什么这样排、哪些东西是量出来的、哪些东西是刻意删掉的。

仓库整体、两个站点共用的部分（历史库、单文件报告、IIFE、Vercel 静态部署）写在 [README.md](../README.md)；报告数据的字段契约、以及 `src/core/report.mjs` 与 `web/` 之间唯一的接口，写在 [docs/REPORT-CONTRACT.md](REPORT-CONTRACT.md)。本文只讲优衣库独有的那些取舍，共通的东西不在这儿重复。

本文里凡是**被合并改动**的地方都标了「合并后」。

三件事没有变，是有意的：

1. **localStorage 键沿用 `uniql.picks` / `uniql.dropped` / `uniql.hidden`**，`deals[].id` 也沿用旧的 `productCode` 值。所以在合并前那份报告里点过的收藏、隐藏过的商品，在新报告里原样还在（契约第五节）。
2. **优衣库图片 CDN 的 ORB 坑没变**：它返回的 `Content-Type` 是 `application/octet-stream`，Chrome 的 ORB 会拦掉跨域引用，报告里会是一片空白。所以商品图必须下到 `reports/uniqlo/img/`，payload 里给的是本地相对路径 `img/u…@561.webp`，**不能**回头去引 CDN。
3. **上市价照旧是攒出来的**：抓的仍是官方原价（`originPrice`），存进 `launch_price` 时取历次快照的最大值。合并后是**空库重新抓的**（没有迁移旧的 `uniql.db`），所以头几天 `launch_price` 必然等于当前原价，降幅看着偏小；等每天 `sync` 攒到几周才是真的上市价。

## 二、抓取：为什么走接口、为什么必须伪装浏览器

### 2.1 前端渲染的 SPA，HTML 里没有价格

`www.uniqlo.cn` 是前端渲染的 SPA，商品列表页的 HTML 里**没有价格**，解析 DOM 拿不到东西。它自己用的公开搜索接口是个 JSON POST，无需登录、无需 token：

```
POST https://d.uniqlo.cn/p/hmall-sc-service/search/searchWithDescriptionAndConditions/zh_CN
```

请求体里带 `pageInfo`（`page` / `pageSize`）、`identity`（按标签过滤）、`rank` 等；回应里 `resp[1]` 是商品数组，`resp[2].productSum` 是总数。原价、现价、限时窗口、商品标签都在里面，所以整条链路上没有一处需要读 HTML。

### 2.2 站点前面挂着 WAF，所以要发真实浏览器 UA

`d.uniqlo.cn` 前面是腾讯云 EdgeOne 的 WAF，会按 UA 拦明显的爬虫。适配器固定发一个真实浏览器（Chrome/120）的 `User-Agent`，并带上 `Origin: https://www.uniqlo.cn` 和 `Referer: https://www.uniqlo.cn/`——这三样一起才过得去。

请求侧的其他防护：单次 `AbortSignal.timeout(30_000)`；失败重试 3 次，退避 `800ms × (i+1)`；翻页之间 `sleep(250)` 别把人家接口打太狠。重试与节流写在适配器自己这一层（迪卡侬那份有它自己的一份），而那个 UA 和两个头更是**这一站独有的**。

### 2.3 抓什么：两个标签，不是全站

`sync` 的商品池是两个标签，各翻一遍再合并：

- `time_doptimal` 限时特优 —— 每周轮换的活动价，下周会涨回去。看到尺码齐、价格合适就该下手。
- `concessional_rate` 超值精选 —— 换季清仓，会一路降到底，但降到最后往往开始断码。

两个标签抓完，还要按 `productCode` 去重：同一件商品会因为落在不同分类里而重复出现，去重时**保留现价更低的那条记录，并把两边的标签合并**（一件商品可以同时是限时特优和超值精选过），最后滤掉 `minPrice <= 0` 的脏数据。

合并后第一次 `sync` 拿到 **885 件**（重抓一遍大约一分钟；旧 README 记的是 877 件——商品池随档期浮动，不该对齐某个固定数）。

标签码除了上面两个，接口还会回 `new_product`（新作商品）、`pickUp`（门店自提）、`revision`（修改裤长）。这三个不参与抓取，只在终端表格的「标签」列里出现，而且 `pickUp` 被显式滤掉——它跟「降不降价」无关。真正的中文译名集中在适配器的 `TAGS` 里（契约要求能读 meta 的一律读 meta）。

### 2.4 字段语义

接口 → 我们的字段，语义值得记一笔：

| 接口字段 | 我们的字段 | 语义 |
| --- | --- | --- |
| `originPrice` | `originPrice` → `origin_price` / `launch_price` | 官方原价。优衣库原价只降不涨，所以历史最高原价 ≈ 上市价 |
| `minPrice` | `price` → `last_price` | 现价（多色/多码中的最低价） |
| `maxPrice` | `extra.maxPrice` | 最贵那档。报告不渲，只留档 |
| `monthlySales` | `monthlySales` → `monthly_sales` | 抓下来存库，**不进报告**——这个字段不能当销量读，依据见本节末 |
| `sales` | `extra.totalSales` | 接口里另一个销量字段。同样**不进报告**：语义未证实，只留档 |
| `season4zhCN` | `season` | 报顶榜单那行小灰字用 |
| `minSize/maxSize4zhCN` | `sizeRange` | 同上，拼成 `S ~ XL` |
| `sex4zhCN` / `material4zhCN` / `styleText4zhCN` / `stock` / `productStoreStockFlag` / `timeLimitedEnd` | `extra.*` | 报告的卡片和列表都不渲染，但留在库里 |
| `identity` | `tags` | 标签数组，页签筛选和卡片 chip 的匹配语义都靠它 |
| `productCode` / `code` | `product_code` / `code` | 前者是主键、也是 localStorage 的键；后者是吊牌号 |

**为什么撤掉了「月销」那一列（2026-09-30 查证）**

报告里原先有一列照抄接口字段名的「月销」，用户会读成「这件商品一个月卖了多少」。查证后发现这个说法站不住：

- **不是我们存错了。** 同一个 `productCode` 对质：库里 `monthly_sales=25911608`，接口当时返回 `monthlySales=25911608`，逐字节一致；写入时的列顺序也逐个核过（`monthly_sales ← p.monthlySales`，25 个参数没有错位）。
- **接口这个字段自相矛盾。** 同一个款、三个颜色：`monthlySales` 分别是 25,911,608 / 133,791 / 77,271，**差 300 倍**。
- **两种可能的解释都被数据打脸。** 若它是月销量（`sales` 是累计），则不该出现「月销 > 累计」——实测 **762/886 件（86%）**都是这样；若它是浏览量（`sales` 是成交量），则不该出现「浏览 < 成交」——实测 **124/886 件（14%）**如此。无论怎么解释都解释不通。

结论不是「它是什么」，而是**它不能当销量读**。假不在数据，在我们**照抄了接口的字段名、替它背书**。这一列因此撤掉；库里的 `monthly_sales` 仍然保留（历史数据，将来要重新研究还在）。

**`extra` 这袋字段是刻意不进 payload 的**：报告的 payload 是上千份商品结构的复制，多一个字段就是上千份。`extra` 只在数据库里；`toCanonical` 把它装满，`buildPayload` 一个不带。

## 三、报告：这一页为什么长这样

### 3.1 报头只剩一行

报头只有一行站点信息：站点名（`meta.label`）、抓取时间，然后是可选的「共记录 N 件」和行尾的兄弟报告入口。这一格现在两家都不开（`showRecorded: false`）：2026-09-30 之前只有迪卡侬显示，后来应要求去掉了。

报头原来还有一排**总账数字**（在售降价 N 件 / 全部买下可省 ¥X / 降幅 ≥ 50% N 件 / 处于历史最低 N 件），现在删了。它们的问题不是不准确，是**对「这一件要不要买」没有任何帮助**——「全部买下可省多少」尤其如此，没人会全买。

**历史最低也一并删了。** 它要靠时间攒：只有一天快照时，「历史最低」必然等于现价，于是每一件商品都挂着「历史最低」的标——一个全都命中的标记等于没有标记，还顺带把终端那张表的整行都染成绿色。数据层照旧在记录（`min_price_ever` / `min_price_at` 一直在写，`is_lowest` 也照算），只是报告不再展示；等快照攒到几周、这个判断真能区分开商品时，再把它接回来。

留下的是每件商品的**上市价 / 现价 / 降幅**——这三个数字直接回答「值不值」；省下多少钱由降幅和现价自己就能算出来，不必再念一遍。

### 3.2 页顶榜单：`RankBoard`

**本期降得最狠的五件**排成榜，放在**整页最上面**：报头之下、筛选页签之上，打开就先看见这一期哪儿在塌。每行是序号（只有第一名标红）→ 名称＋季节/尺码 → 上市价 / 现价 / 降幅。

只摆第一件的话，想看第二三名还得自己往下翻、自己排序，所以一次排五件。件数用汉字且随实际条数走（`CN = ['一','二','三','四','五']`）——只剩 3 件的时候不该写成「五件」。

三件事是刻意这样定的：

1. **它不跟着工具栏的筛选走。** 它答的是「这一期整体哪儿在塌」，和「筛出来的那批商品」不是同一个问题；跟着筛只会让它和正下方第一排卡片重复一遍。所以它读的是未经过滤的 `deals`。
2. **排序用精确降幅，不是四舍五入后的整数百分比。** 三件都显示 `-74%` 时，真实降幅是 `73.83% / 73.83% / 73.58%`，顺序仍由真实值（payload 里的 `rate`）决定，和工具条里按「降幅」排序的结果一致。降幅完全相同（同样的上市价降到同样的现价）才比谁省得多。
3. **它留在 `.toolbar` 外面、并且在它上面。** 它看着是紧挨着页签的一栏，但塞进粘性盒子里的话（不管盒子是 `.toolbar` 还是它内部的某一层），它要么跟着页签常驻屏幕顶，要么因为粘性元素只能在自己父盒子里滑动而把页签的「整页粘住」一起弄丢——`.toolbar` 的高度只到榜单底部，父盒子一到底页签就不粘了。放在外面、且放在前面，页签照旧整页粘着，榜单自己滚走。

榜单上那个降幅角标是**黄底**的（`.rank__off`）——整份报告里黄角标只剩这一处，卡片上的降幅是红字。

**这一整块是优衣库独有的**（`features.rankBoard: true`）。迪卡侬那份没有，是选择不是少了什么：迪卡侬的商品名下面是「品牌 + 编号」，榜单里再念一遍品牌很啰嗦，而优衣库的商品名本身就够短，摆得下一张榜。

### 3.3 粘性工具栏

工具栏整页钉住：滚到 877 件的中段想换个页签，不该一路滚回顶部。它是 `flex-wrap` 的，换行数随宽度变，高度也就跟着变。九档实测：

| 宽度 | 1440 | 1280 | 1100 | 900 | 761 | 760 | 620 | 480 | 380 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 工具栏高度 | 57 | 57 | 57 | 57 | 57 | 57 | 57 | 57 | 91 |
| 工具栏内容 | 页签 + 搜索 | ← | ← | ← | ← | 只剩页签一行 | ← | ← | 页签自己换成两行 |
| `position` | sticky | sticky | sticky | sticky | sticky | sticky | sticky | sticky | sticky |

撤掉排序控件（那个下拉框 + 升降序按钮是工具条上最宽的一组）之后，这一行**在所有宽度上都不再折行**：1440～480 全是 `57px`。唯一的例外是 380——页签自己换成两行，变 `91px`。

**踩过的坑：`position: sticky` 的元素只能在自己的父元素盒子里活动。** 工具条原来被包在自己的 `.wrap` 里，父盒子跟它一样高，于是它其实从来没粘住过。现在是三层：`.toolbar`（整页宽、只负责粘）＞ `.wrap`（对齐）＞ `.toolbar__row`（flex 排布＋那条内缩的发丝线），外壳的父盒子是整页高的 `#root`，才真的粘得住。

窄屏（≤760）这一档只留页签一行、**并且继续钉住**：搜索撤掉，工具栏就剩 `57px`（手机的 7%）。实测滚到 1800 处 `.toolbar` 停在 `top: 0`、高 `57px`。

**0.5px 的坑**：工具栏真实高度是小数（900 宽下 `91.5px`），和下边内容之间会留下 0.5px 没有白底盖住——滚动时从这条缝里会透出行内容，2x 屏上正好是一个物理像素宽的闪烁细线。修法是让工具栏自己的白底往下多铺 1px（`box-shadow: 0 1px 0 #fff`），它不参与布局、也就不会改高度。

> 合并时这一档曾经两家不一样：优衣库钉住、迪卡侬滚走（依据是迪卡侬那时有两行 104px，常驻太占地）。后来应要求把迪卡侬也收成一行并钉住，于是两家在这一档完全一致（见 [DESIGN-DECATHLON.md](DESIGN-DECATHLON.md) 4.5）。

### 3.4 只有大图一种视图

优衣库分类页那种卡片墙：图大、铺满整列，翻的时候一眼就能看清是哪件衣服。卡片从上到下是图 → 名称 → 价格 → 比例条。官网卡片名称上方那行性别/尺码小灰字、名称后面的货号都省了：几百张卡片各念一遍帮不上忙，细节去商品页看，搜索仍认货号。

商品图是 **3:4 的画框**（和官图同比例，图能填满不浪费），**点一下直接去官网商品页**（新标签打开）——和官网一样，认准了是哪件就点图，整张图都是热区。

没降价的商品（手动 `track` 进来、还没打折的）不画标尺——硬画就是一根 `-0%` 的空条——改写成「尚未降价，正在替你盯着」，价格也从红色退一档到次级灰，因为**看着像在打折比不打折更误导**。

**排序固定是「降幅从大到小」**，没有排序入口（2026-09-30 撤掉了工具条上那个下拉框 + 升降序按钮，连同 payload 里的 `meta.sorts`）：捡漏只有这一种排法是有意义的。比的是精确的 `rate`，不按四舍五入后的整数百分比——三件都显示 `-74%` 时顺序仍由真实值决定；`sort` 是稳定的，所以降幅完全相同的那些保持 SQL 那边的顺序。

> **原先还有一个「列表视图」**（一张「门店价签」式的表：左边 `84px` 小图、右边价格从上市价坍缩到现价、最右一根降价标尺），2026-09-30 应要求撤掉了——大图够用。连带删掉：`DealRow` / `ColumnHeader` / `PriceScale` 三个组件、整套表格 CSS（含表头粘性用的 `--headtop` 机制、`--cols` 轨道、行内价格那套 18px 令牌）、payload 里的 `meta.columns`（先换成 `meta.sorts`，2026-09-30 又把排序入口一起撤了，那份声明也就没了）、四个只服务列表的开关（`rowMetaLine` / `rowChips` / `flatWasDash` / `scaleLayout`）。CSS 从 40.4KB 降到 29.5KB。

### 3.5 卡片和列表上刻意不做的事

- **卡片上不标促销类型。** 官网每张列表卡片都挂一个「限时特优 / 超值精选」的方框标签，这一页几百张卡片就是几百遍同一句话——促销类型在工具条页签里筛一次就够，卡片上让位给价格。所以 `chipTags: []`，`stickerTags: false`，卡片图上也没有角标。
- **「待拔草」不另挂标签。** 爱心收了就是实心品牌蓝，同一件事讲两遍只是把这一行挤得更满（`trackChip: false`）。
- **榜单里那行小字不带编号**，只剩季节/尺码。
- **不标促销类型、不显示历史最低、不显示总账数字**——这三条上面都给了理由，汇总在第八节。

## 四、视觉：版面量自官网，配色和价格排版跟迪卡侬那份统一

**版面尺寸**不是「看着像」，是把 uniqlo.cn 的**计算样式**读出来照抄的（字号、缩略图 3:4、列宽、卡片网格）；**配色、价格排版、动作图标**则统一用迪卡侬那份报告的一套，两份报告来回切换不用重新认颜色。这条分工在合并后由 `data-site` 与 `meta` 实现：几何挂在 `[data-site="uniqlo"]` 下，配色是两家共用的一层。

### 4.1 配色与价格排版（跟迪卡侬一致）

| 项 | 值 | 用在哪 |
| --- | --- | --- |
| 墨 / 次级 / 最淡 | `#000f17` / `#616161` / `#b3bac3` | 正文、次级文字、最淡的图标 |
| 品牌蓝 | `#3643ba` | 链接、hover、页签选中、收了的那颗爱心 |
| 黄 | `#ffcd4e`（角标墨字 `#101010`） | 降幅角标（这一份只剩榜单那一处） |

| 发丝线 / 浅底 | `#eff1f3`、`#d9dde1` / `#f5f4f5` | 表格分隔、标尺轨道、浅底 |

| 上市价 | `15px` / `#616161` / `text-decoration: line-through` | 上市价格子。官网是 `12px`，**这里刻意放大到 15px**（2026-09-30 用户要求「让用户知道原来原价那么高」）——12px 划线的灰字扫过去根本看不见，等于白记了上市价；主次改由颜色区分（原价次级灰、现价红），不再靠把原价缩到看不见。榜单里那一处同步放大（现价 22px 仍压得住） |
| 降幅 | 黄底直角角标（`12px` / 高 `16px` / 内衬 `0 4px`） | 只剩榜单那一处（合并后卡片和列表的降幅都改成了红色 `12px` 数字） |
| 零值 | 官网写 `¥ 0`，**不带小数** | 标尺右端刻度（由 `meta.currency.zero` 给） |

两处刻意与 uniqlo.cn 不同、跟着迪卡侬走：

1. **上市价划删除线（且不再缩得很小）。** 优衣库官网只用「变小 + 变灰」弱化原价，迪卡侬官网是划线的；既然视觉统一走迪卡侬，划线也一起跟过来。字号则连同迪卡侬那份一起放大到 15px（官网是 12px）——理由见上表：看不见的原价没有意义。划线只在**真降了**的时候才画（`row__was--cut` / 卡片上的 `cut`），没降的原价等于现价，划它没意义。
2. **现价的红色倒是刻意从官网留下的**（迪卡侬那份用的是墨色）：价格本来就是这页的主角，红是它的冲击力所在；没降价的价格退成次级灰，红色只属于降了的价。

### 4.2 大图视图：照官网分类页实测的网格

网格尺寸是在 `uniqlo.cn/c/2wdrsnskrt.html`（女装短裙分类页）和 `/timelimit.html`（限时特优页）上把卡片和图片的几何量出来照抄的：

| 项 | 官网实测值 | 用在这页 |
| --- | --- | --- |

| 卡片间距 | 水平 **0**，垂直 `24px` | `gap: 24px`（官网横向靠列宽吃掉，这里留一点更透气） |
| 卡片本身 | 无 padding、无边框、无背景 | 同 |
| 商品名 | `15px` / `400` / `rgb(27,27,27)`，最多两行 | `.card__name`（`-webkit-line-clamp: 2`） |
| 图→文字间距 | `52px`（含卡片内的留白） | `margin-top: 16px` |
| 促销价 | `16px` / **`700`** / `rgb(255,0,0)` | `.card__now` |

**图片写 CSS `aspect-ratio`，而不给 `<img>` 写 `width`/`height` 属性**：属性会变成 used height、把 `aspect-ratio` 顶掉，图就被塞进一个非 3:4 的框里留白（实测过一次，卡片图变成 `318×392`，比例 0.812 而不是 0.75）。所以卡片图只给 `src`。列表缩略图那一格的宽高（`meta.thumb`）本来是准备写成属性的——优衣库这一版比例和图片一致，写上能让浏览器在 CSS 到位之前就先占对位——但当前 payload 里没有 `thumb` 这一项，渲染结果同样是「没有属性、形全由 CSS 定」，和卡片图一样。

响应式验证过 6 档宽度，列数 4 / 3 / 3 / 2 / 1 / 1，每一档图片比例都精确 0.75、横向溢出 0。

## 五、图片：为什么是 561 档

> 顺带一条两家共用的规则（2026-09-30 加）：**没图的商品不上榜**。抓不到图、或者官网自己就没图，卡片上只剩一个灰框，看不到是什么东西也就没法买，所以生成时就剔掉（见 [DESIGN-DECATHLON.md](DESIGN-DECATHLON.md) 第五节）。这一站目前没有这种商品——878 件全部有图。

官方只提供两档能用的尺寸（中间档如 160 / 320 一律 404）：

| 档位 | 实际尺寸 | 单张体积 |
| --- | --- | --- |
| 80 | `120×160` | 2.9KB |
| 561 | `1200×1600` | 约 94KB |

80 档在大图视图里根本不够看——卡片在 1440 宽是 `318px`、单列窄屏能到 `513px`，Retina 下要 `600~1000px` 的源图——所以用 561 档：全站约 88MB，CDN 吞吐 6MB/s，一次抓完二十几秒。

档位写在 URL 路径里（`.../main/first/561/1.jpg`），所以适配器的 `sizeVariant` 是个纯字符串替换：把 `/first/<任意数字>/` 换成 `/first/561/`。这条规则**留在站点这一侧**，共享核心只负责「把 URL 交出去、把字节收回来」。文件名带档位与格式（`u0000000072656@561.webp`），换档位/换格式时不会把旧的当缓存命中。
   落盘前统一过一次 **WebP q82**（见 core/images.mjs 的 `encode`）：官网给的 JPEG 同样清晰度下
   实测大一半（6 张样本 488KB → 247KB），而首屏那十来张图是整页最大一笔流量。
   老缓存里的 JPEG 会被**就地转换**再删掉，所以本机和 CI 的缓存都能平滑升级；没装 sharp
   （`npm ci --omit=dev`）就退回 JPEG，扩展名跟着变，上游拿到的路径永远是对的。

优衣库只需要**一张**图，所以它的候选链长度是 1；共享核心统一按「候选链」处理（一张一张试，第一张下来了就停），逻辑完全一样。这一站没有迪卡侬那种「主图 410、副图还在」的问题，但共用这套代码不损失任何东西。

4xx 与 5xx 区别对待：4xx 是「这张图不存在」，重试没意义，直接换候选；5xx 或超时是网络抖动，同一张图再试一次。

## 六、字体：内嵌思源黑体子集

### 6.1 来龙去脉

官网的字栈是 `UniqloProRegular` 配 `syht_Regular`（思源黑体）。品牌字体不能内嵌，思源黑体可以——它是 **Apache License 2.0**，而且从优衣库自己的 CDN 就能拿到：

```
https://www.uniqlo.cn/public/bin/Font-syht/SourceHanSansCN-Regular.otf
https://www.uniqlo.cn/public/bin/Font-syht/SourceHanSansCN-Medium.otf
```

首次跑 `report` 会下载这两个文件到 `data/fonts/`（各约 8MB，只下一次），然后用 `subset-font` 按**页面里真正出现过的字**裁剪成 woff2 内嵌进报告。裁剪用的字符集是「整个前端 bundle 的源码 + 本次数据 + 页面标题」——UI 文案都在 bundle 里，商品名在数据里，这样不会漏字，也不用手工维护字符表。全站几百件商品的名字也就用掉几百个汉字，裁完约 200 字节/字，报告因此明显变大（合并前实测从 0.7MB 长到 1.0MB 量级）。

想省掉这部分体积，用 `deals uniqlo report --no-font`，版面不变，中文退到系统字体（macOS 上是冬青黑体）。

### 6.2 为什么 Medium 挂在 700 这个槽位上

取两档就够：正文 Regular（400）、强调 Medium。优衣库中文的强调用的是 Medium，**不是 Bold**——官网的标题规则是 `b,h1..h5,th{font-family:LTMedium;font-weight:400}`，汉字从不压重黑。所以这里把 Medium 挂到 `700` 这个槽位上，让 `font-weight: 700` 的汉字落在 Medium 上，正好是官网的观感。

这两条「用哪个字体、挂到哪个字重槽位上」是**站点自己的观感问题**，所以在适配器的 `fonts.faces` 里声明；共享核心只负责下载、子集化、拼 `@font-face`。`fonts: null` 就是这一站不内嵌（迪卡侬那半就是这样）。

### 6.3 许可与署名

> 内嵌的是 Apache-2.0 的思源黑体，版权归 Adobe（Copyright © 2014 Adobe Systems Incorporated）。品牌字体 `Uniqlo Pro` 没有内嵌。

这段声明由适配器写成 `fonts.notice`，交给 `buildFontCss` 写成 `@font-face` 旁边的一条 **CSS 注释**（`/* … */`），只有**真的内嵌成功**时才写（返回 null 就不写，报告退系统字体栈）。

**署名不能省**——那份子集是 Apache-2.0 的，分发包里必须保留版权与许可文字。放在内嵌 CSS 的注释里就满足这一点（注释随同一个 HTML 文件发出去），所以 2026-09-30 撤掉页脚那行可见署名时，这条注释原地保留。

想让西文也像官网那样是 `Uniqlo Pro`，只能在自己机器上装；装不到就退到 `Helvetica Neue`，中文仍然走内嵌的思源黑体。**中文这一侧不能将就**：macOS 上如果没有 PingFang，字体栈会掉到 Hiragino Sans GB（冬青黑体），和思源黑体的观感差别肉眼可见——整页会呈现出一种老 macOS 应用的味道，而不是现代中文网页。

## 七、收藏 / 不再出现：两个图标，两本账在浏览器里

它们在**价格行的最右端**（`margin-left: auto` 把它们顶到行尾，正好和现价、划线上市价排在同一行；降幅数字不在这行——它在下面那根比例条的条尾）。两个灰线图标，用 **lucide**（`Heart` / `EyeClosed`，16px）：

- **爱心** —— 这件进「待拔草」，工具栏那个页签立刻 +1。爱心**一律实心**，形状不表示状态，收没收改由颜色说：淡灰（`--ink-faint`，`#b3bac3`）静着，收了转品牌蓝（`#3643ba`）——所以卡片上不再另挂 `★ 待拔草` 标签。
- **闭眼** —— 这个款从榜上**永久**消失：刷新、重新生成报告都不再出现。按款删（写两个键：商品编号 + 吊牌号），同款其他颜色一起走——优衣库一个款多个颜色、名字一模一样，只删一个的话另一个照旧在榜上，会让人以为「删了怎么还在」。**没有放回**——有些东西就是不想见第二次，而一颗「已隐藏 `N` 件 · 放回」等于天天提醒你「这儿还堆着你藏起来的东西」（2026-09-30 把按钮和 `restoreHidden` 一起删了，`hidden` 从此只增不减）。代价是误点没法撤，只能清浏览器存储。

### 7.1 这两个动作搬过两次家

最初是一层盖满整张图的深色遮罩，两个动作写成「收藏 / 烂货」两行大字、悬停才浮出来——遮罩**把衣服挡住了**，而这一页的全部意义就是看清衣服。改成图右下角两个白色小方块后，图恢复成了链接，但图标仍然压在照片上，而右下角正是最容易看清下摆的位置。现在它们离开图片：图彻底还给「点一下去官网」，动作贴着价格读。

图标**不带底色、不带边框**，因为同一行已经有角标，再加两个方块就太重了。不用垃圾桶、也不用叉号：垃圾桶填成实心就是一只黑桶，跟一排数字排在起又重又钝；叉号是两条硬邦邦的直线，跟圆润的爱心并排像两个体系的东西。闭眼是「不看了／不显示」最安静的说法，也正好对上这件商品的状态——它没被销毁，只是从这张榜上隐掉了。

尺寸也不单独配：lucide 全系画在 24 格上，但字形占多大差很多。爱心铺满 2→22，`EyeClosed` 也铺满 2→22，所以两者同尺寸（都量到 `14.6px` 的墨迹跨度）；而曾被换掉的那颗叉号只从 6 画到 18，同尺寸下只有爱心的六成宽，得单独放大到 24 才追得平——**换图标时不能默认同 size 就一样大，得看字形的墨迹跨度**。描边保持 lucide 默认的 2，`EyeClosed` 内部是弧形，加粗会糊。

文字（「收藏」/「不再出现」）留在 `.sr-only` 里给读屏，鼠标停上去还有 `title`，屏上只有图标。

### 7.2 账本

两本账都存在**这台电脑的这个浏览器**里（`localStorage` 的 `uniql.picks` / `uniql.dropped` / `uniql.hidden` 三个键，前缀来自 `meta.storagePrefix`）。单文件报告没有服务端可写，这是唯一能落地的地方，好处是报告重新生成、重新抓取都还在，代价是换浏览器、清缓存就没了；`deals uniqlo dev` 起的是 `http://localhost`，存储区和双击打开的 `file://` 不是一个，两边收藏互相看不见。

「待拔草」是**三份来源合出来的**：终端 `deals uniqlo track` 进来的 ∪ 报告里点过「收藏」的 − 报告里点过「取消收藏」的。那个减号（`uniql.dropped`）不是多余的一层，因为命令行**只有 `track`、还没有 `untrack`**：对一件已经 `track` 的商品，取消收藏只能在报告这边记一笔把它压住，否则刷新一下它又从数据库里冒回来。

**键名不许改**（契约第五节）。合并时 `deals[].id` 沿用了旧的 `productCode`，前缀也沿用 `uniql`，所以旧报告里点过的账在新报告里还在。

### 7.4 断码时，名字那一行显示尺码

2026-09-30 加的一条规则，最终定成这样：**名字那一行二选一**——

| 这件商品 | 那一行显示 |
| --- | --- |
| 码全（或根本拿不到尺码信息） | **商品名**（绝大多数商品走这条） |
| 断码 | **剩下的尺码**，不显示名字 |

用户原话是「图片已经看得够清楚，我不关心商品名，但我关心还有什么尺码」——捡漏时真正决定
买不买的是「我的码还在不在」。名字没丢：断码的那些卡片把名字挂在链接的 `title` /
`aria-label` 上，鼠标停一下能看到，读屏也读得到。

> 走过的几版一起记下来，免得照着旧说明改回去：
> 走过的几版一起记下来，免得照着旧说明改回去：
> ① 把商品名**整行换成**尺码（用户否掉：名字要回来）；
> ② 名字一行 + 尺码另起一行（12px 的详情行，用户看过后改成下面第 ⑤ 条）；
> ③ 码全时写个 `all`（用户否掉：不用显示）；
> ④ 尺码短名无脑取词表第一段，于是在裤子上冒出「W28 · 76cm · 79cm · 82cm · W40…」
> 这种半中半英的混排（用户报的）→ 先改成统一取 W 段，结果「W28 · W30 · W31」用户还是读不出来
> （他要的是「XL 这种、或者 150cm 这种」）→ 最终**一律换成厘米**，见下面第 2 条；
> ⑤ 有缺档时把剩下的码全列出来，剩 10 档以上的那一行会折成第二行、把同排卡片的价格线顶歪
> → **超过 6 档就只写「剩 N 档」**；
> ⑥ 名字一行 + 尺码一行还是太挤 → **合成一行二选一**：码全显示名字、断码显示尺码
> （最终形态，就是上面那张表）。

数据从哪来（三段，缺一不可）：

1. **在售的码**：搜索接口每个商品带一个 `size` 数组，里面是**有货的内部码**，如
   `["SMA003","SMA005","SMA006","SMA004"]`。已核对该数组确实是「有货」的子集：
   实测有 `在售[XS] / 该款全部[XS,S,M,L]` 这种样本。
2. **码 → 显示名**：同一个接口带上 `pageInfo.withSideBar: 'Y'` 时，侧边栏里有一段
   「尺码」词表，**69~95 档、13 个家族**：`SMA002=XS`、`CMA080=80cm`、
   `CMD070=W28/28英寸/28码`、`SHC225=36/225mm/22.5cm`、`SIZ999=均码`…
   每次 `sync` 刷一遍，存进 `size_vocab` 表（**不写死在代码里**——它是接口给的数据，
   新家族出现时不用改代码）。卡片上**一律显示厘米**（`W28` 这种美制腰围码没人读得出来）：
   串里明写了 cm 就用它（`73cm/W29/…` → `73cm`、`36/225mm/22.5cm` → `22.5cm`）；
   CMD 家族**码里的数字就是厘米**（实测词表里带 cm 的 7 档全部等于码里数字，所以没写 cm 的
   12 档照补：CMD070 → 70cm；注意**不能**拿英寸乘 2.54——官网的腰围是 3cm 一档的梯子
   73/76/79/82/85/88/91，W32 写的是 82cm 而不是 81.3cm）；按英寸给的 INS 家族则乘 2.54
   （INS023 → 58cm，正对得上同款尺码范围里的「150/58A」）；其余家族第一段本来就是对的
   （字母码 `XS`、童装 `80cm`、袜码 `25-27cm`、内衣 `AA65`、`均码`）。
3. **是不是「都有」**：主判据是**同家族里在售的码连成一段**——不拿
   `minSize4zhCN ~ maxSize4zhCN` 直接去比，因为那个范围串的写法和词表并不一致
   （裤子写 `160/70A ~ 190/120C`，词表里却是 `W28/28英寸/28码`），比不出可靠结果。
   但「连续」有个缺口：该款 `S ~ XL`、只剩 XS 时，只有一档当然连续，于是被当成「码全」——
   所以再加一道**只降不升**的校正：范围串两端**能在词表里认出来**时（字母码 `S ~ XL`、
   厘米码 `110cm ~ 160cm` 都能认），在售的码只要有一个落在范围外就不算「都有」；
   认不出来（CMD/INS 那种写法）就跳过，维持连续性判断。
   这道校正实测把 45 件原被误判成「码全」的商品（主要是童装厘米码）改回了「显示剩余尺码」
   （在售 881 件里：码全 646 件、有缺档 215 件）。

**商品名也跟着截短了**：官网名字是「主名/一堆形容词」拼的（「高性能修身防皱衬衫/长袖衬衣
商务通勤」），斜线后面那截是搜索/分类用的，卡片上没人看——只留斜线前面那一段。完整名字
没丢，在库里的 `extra.fullName`（不进 payload）；终端 `list` 里也是短名。

**每一档是一个 `<kbd>` 方块**（用户要的「像键盘键帽」）：直角、发丝边（`--rule`）、
浅底（`--surface-2`），跟工具条上那些页签是同一种语言；方块里的字用等宽体，数字和字母
排出来整齐。语义上 `<kbd>` 本来是「用户输入」，这里纯借它的方块外观——它没有 ARIA role，
读屏不会多念；用真元素还白拿一层兜底（样式没加载时它是等宽字，照样读得出来）。
方块之间没有分隔符，所以无障碍文案另走 `plain` 字段（'XS · 3XL'）。

**那一行最多列 5 档**（`MAX_SIZE_LABELS`）。这个数是量出来的，不是拍的，而且**换成方块之后
重量过一次**：方块比「 · 」分隔宽，1440 宽时那行可用 322px，童装厘米码（`110cm` 这种）
只到 5 档（6 档就折行），腰围厘米码到 6 档、字母码到 8 档——取最保守的 5。
超了就只写「剩 12 档」——列不全还不如报个数。

**实测覆盖（当时在售 881 件）**：97.7% 能给出尺码（码全 691 件、有缺档 170 件；有缺档的
里面剩 2~6 档有 151 件（列出来），剩 7 档以上 19 件（只报个数）），剩 2.3%（睡衣、帽子、手套那 20 件）**接口连
`size_range` 都没给**，那 20 张卡片这一行空着（高度照占，所以价格线仍然对得齐）。

> WAF 直接拒绝（HTTP **567 AccessDeny**，正文就一句 AccessDeny），所以拿不到
> 「详情接口里的尺码+库存」；而 `CMD079` 这种码光看数字推不出显示名

## 八、终端与刻意不做的事

### 8.1 终端那张表

优衣库那份的列（`tableColumns`，由站点声明、共享核心只负责画）：`编号 | 商品 | 上市价 | 现价 | 降幅 | 省 | 标签`。

没有品牌列也没有销量列，第 7 列就是标签——这是和迪卡侬那份最直观的差别（迪卡侬第 7 列是品牌）。标签列滤掉 `pickUp`，其余按 `TAGS` 译名。（原先第 7 列的「月销」已按上面查证的结论撤掉。）

`list` 的排序口径：`--sort rate|saving|newest`；`--tag time_doptimal|concessional_rate`；默认门槛降幅 ≥30%。`track <编号>` 的编号可以输吊牌 6 位数，也可以直接贴商品页地址（`parseCode` 从里面抠 `\d{6}`）；手动盯的商品会按第一个命中的标签解释「这是什么性质的降价」——超值精选＝清仓，限时特优＝下周可能涨回原价。

### 8.2 页脚：已撤（2026-09-30）

报告**到商品网格就结束了**，没有页脚。原先那一块（名词解释五条、数据来源、版面说明两条、字体署名）全部来自 `meta.foot` / `meta.fontNotice`，应要求整块删掉——那几段没人看，页面上占着一屏。

连带删掉的是：payload 里的 `foot` / `fontNotice` / `source`（`source` 其实早就没人读了）、`App` 里的页脚块、`.foot` 那一套样式（共用 + 两家共 9 条）。副作用是内嵌字体的**子集变小了**（页脚那些独有汉字不再进子集），报告从 0.9MB 掉到 0.8MB。

字体署名是唯一不能跟着删的东西，见 6.3：它落在 `@font-face` 旁边那条 CSS 注释里，随文件走、页面上不显示。

### 8.3 报头行尾那组入口

`meta.links`（数组）排的就是行尾那一组：

1. **另一家的报告**（来自适配器的 `report.crossLink`）——两份报告互认是一家工具做的，
   指向 <https://goodprices.online/decathlon/> 与 <https://goodprices.online/uniqlo/>。
2. **尾货市集**（`https://goodprices.online/market/`）——全站共用，由核心在
   `buildPayload` 里补进来，适配器不用管；只有 Cloudflare 那条部署路径给 `marketHref` 时才加
   （Vercel 上没有这一页）。见 [MARKET.md](MARKET.md)。

⚠️ **只有第一个入口**能写 `margin-left: auto`。两个都写的话，flex 会把剩余空白**平分**给它们，
两个链接之间就空出一大块——2026-09-30 加了第二个入口之后露出来的，改成
`.masthead__cross:first-of-type { margin-left: auto }`（实测两个入口之间 14px、
最后一个的右边缘正好贴住行尾）。

### 8.4 刻意不做的事（汇总）

| 不做 | 为什么 |
| --- | --- |
| 不显示总账数字（在售降价 N 件 / 全部买下可省 ¥X / 降幅 ≥50% N 件） | 对「这一件要不要买」没有任何帮助；「全部买下可省多少」尤其如此，没人会全买 |
| 不显示「历史最低」 | 一天快照时它必然等于现价，全都命中等于没有标记；数据层照记，等攒够再接回来 |
| 卡片上不标促销类型 | 几百张卡片就是几百遍同一句话，页签里筛一次就够 |
| 不另挂 `★ 待拔草` 标签 | 实心蓝爱心已经在说这件事 |
| 不用垃圾桶 / 叉号当「不再出现」 | 垃圾桶实心太重；叉号两条硬直线跟圆润的爱心不是一个体系 |
| 不给卡片图写 `width`/`height` 属性 | 属性变成 used height 会顶掉 `aspect-ratio`，图被塞进非 3:4 的框里留白 |
| 不内嵌品牌字体 `Uniqlo Pro` | 迅销的品牌资产，不能内嵌；西文退 `Helvetica Neue` |
| 不硬画没降价商品的标尺 | 一根 `-0%` 的空条看着像在打折，比不画更误导；改写「尚未降价，正在替你盯着」 |
| 不在报告里引 CDN 图片 | ORB 会拦成空白（且商品下架后图会 404）；一律用本地缓存 |

### 8.5 抓取节奏

优衣库的降价节奏：**每周二**调整价格、**每周五**上新一期限时特优。所以建议每天 `sync` 一次攒历史（现在由 GitHub Actions 每天北京时间 09:00 自动跑一轮，见 [README.md](../README.md) 的「自动化」一节）。
